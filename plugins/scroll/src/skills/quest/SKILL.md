# quest — 리드/작업 세션 흐름

```
⓪ 요구사항(리드) → 작업 세션 열기(리드) → ① 설계 → ② 코드 전 검토 → ③ 구현 → ④ 코드 뒤 검토 → ⑤ 리뷰 반영 → ⑥ 마무리 → 합치기(리드)
```

일 하나를 두 세션이 나눠 돈다. 리드 세션은 요구사항을 쓰고 작업 세션을 열고 합친다. 작업 세션은 리드가 연 워크트리에서 ①~⑥을 스스로 결정·기록하며 끝까지 가고, 사용자에게 묻지 않는다(사용자는 리드까지만 대화한다).

## 누가 무엇을

| 누가 | 무엇 | 어떻게 |
| --- | --- | --- |
| 리드 | ⓪ 요구사항 — 요구사항 파일·작업 목록 줄, 커밋 `<ID> req: …` | 아래 "리드 몫" |
| 리드 | 작업 세션 열기 | 부명령 `open` |
| 작업 세션 | ①~⑥ — 단계마다 `step <단계>`로 들어가 나온 안내를 따른다 | 아래 "작업 세션 몫", 단계별 안내 `steps/<단계>.md` |
| 리드 | 결정 요청에 답하기·막힘 풀기 | 아래 "작업 세션과 주고받기" |
| 리드 | 합치기 — ① 확인 → ② deliver → ③ 치우기 | 부명령 `merge` |

## 부르는 법

스크립트는 입구 하나를 전체 경로로 부른다 — `python3 "${CLAUDE_PLUGIN_ROOT}/src/scripts/quest/main.py" <부명령>`. 세션 PATH에 싣는 짧은 이름은 없다. 작업 저장소(또는 작업 워크트리) 안에서 부른다. 이 문서에서 "부명령 `end`"처럼 이름만 쓴 곳도 이 꼴로 부른다.

| 부명령 | 누가 | 무엇 |
| --- | --- | --- |
| `open <ID> --lead <리드 세션 이름>` | 리드 | 작업 세션 열기(먼저 `--dry-run`) |
| `step <단계>` | 작업 세션 | 단계에 들어가기 — 앞 단계 커밋 확인, 그 단계 안내 찍기, 지금 단계 기록 |
| `status <ID>` | 누구나 | 단계 시각(커밋 제목으로 찾은 단계·첫 시각, 빠진 필수 단계) |
| `end <ID>` | 작업 세션 | 끝 확인 |
| `base <ID>` | 작업 세션 | 작업 범위 기준 커밋(검토 범위 `<base>..HEAD`) |
| `carryover` | 작업 세션 | 넘길 일 장부·작업 번호 확인 |
| `merge <ID>` | 리드 | 합치기(먼저 `--dry-run`) |
| `guard`·`hold` | 플러그인 훅 | PreToolUse·Stop 훅(아래 "훅이 하는 일") |

## 이름과 설정

경로·이름은 프로젝트 저장소 뿌리의 `.satchel/quest.json`에서 온다 — 묶음 넷 — `branches`(같이 씀)·`quest`·`session`·`deliver`. 필수 `branches.integration`·`session.terminal`, 선택 `quest.quests`·`quest.guide_docs`·`quest.lead`·`quest.rule_docs`·`session.model`·`deliver.verify`(custom 터미널이면 `session.launch`·`session.close`). 키 표·고정·셈 값은 플러그인 README "설정". 막기 목록·시험 파일 판정·단계 규칙은 프로젝트 설정이 아니라 플러그인 규칙 `src/rules/*.json`(작업 세션에게 지키게 하는 규칙), 터미널 프리셋은 플러그인 `src/presets/terminals.json`이다. 이 문서의 이름:

- `<ID>`: 작업 ID — 고정 꼴 `Q-NNN`. `<리드>`: 설정 `quest.lead`(기본 `lead`).
- `<기록 폴더>`: 설정 `quest.quests`(기본 `.agents/quests`). 작업 하나가 `<기록 폴더>/<ID>-<슬러그>/`(`<작업 폴더>`).
- `<통합 브랜치>`: 설정 `branches.integration`(필수). 작업 브랜치는 고정 꼴 `quest/<ID>-<슬러그>`.
- `<안내 문서>`: 설정 `quest.guide_docs`(기본 `AGENTS.md` — 규칙 색인·사용자 결정 패턴 같은, 결정 전에 읽을 문서). 규칙 문서는 설정 `quest.rule_docs`의 `patterns`에 맞는 문서 — 비거나 없으면(기본값) "바뀐 규칙 문장" 확인이 꺼진다(`retro.md` 그 절도 두지 않는다).
- 메시지 꼴: 작업 세션 → 리드 `[<ID> → <리드>] …`, 리드 → 작업 세션 `[<리드> → <ID>] …`(SendMessage — 안 보이면 `ToolSearch` `select:SendMessage`로 불러온다). 작업 세션의 전달이 두 번 실패하면 지시 장부에 `| 대기: 리드 — 전달 실패`로 남기고 일은 이어 간다(회고에도 한 줄) — 리드는 알림이 안 와도 장부·커밋으로 진행을 본다.

## 기록

- 작업 폴더 `<작업 폴더>/`의 파일 넷: `requirements.md`(리드 — 무엇을 왜, 범위, 수용 기준, 결정 번호 범위)·`plan.md`(작업 세션 — 잰 코드 사실·결정·할 일·코드 전 검토·구현하며 바뀐 것)·`review.md`(작업 세션 — 코드 뒤 검토 요약과 반영 대조표)·`retro.md`(작업 세션 — 끝 검증·어긋난 것·닫을 장부 줄·넘길 일). 틀은 이 스킬 `templates/`(`templates/requirements.md`·`templates/plan.md`·`templates/review.md`·`templates/retro.md`). 리뷰어 보고는 `<작업 폴더>/agents/<이름>.md`.
- `<작업 목록>`: `<기록 폴더>/README.md`(`## 작업 목록` 표 `| ID | 작업 | 상태 | 결정 |`) — 번호의 근거. 리드가 쓰고, 합칠 때 `끝`으로 바꾼다.
- `<장부>`: `<기록 폴더>/carryover.md`(넘길 일 장부 `| ID | 출처 | 받는 쪽 | 내용 | 상태 | 근거 |`, 줄 ID는 고정 꼴 `C-NNN`) — 이 흐름 밖의 몫과 작업이 실을 줄. **리드만 쓴다** — 작업 세션은 장부를 고치지 않고(세션 deny) 회고 `## 닫을 장부 줄`·`## 넘길 일`에 적고, 합치기가 옮겨 적는다.
- `<결정 폴더>`: `<기록 폴더의 부모>/decisions`(`NNNN-<이름>.md`, 머리 `작업: <ID>`) — 다음 작업도 따를 판단만, 요구사항의 결정 번호 범위 안.
- 단계는 커밋 제목으로 남는다(아래 "단계와 커밋", 정본 플러그인 `src/rules/flow.json`). 단계 시각은 `python3 "${CLAUDE_PLUGIN_ROOT}/src/scripts/quest/main.py" status <ID>`.
- 작은 일: 한두 줄 문서 고침은 리드가 `<통합 브랜치>`에 직접 커밋한다(작업 ID·기록 폴더 없음).

| ⑤ 리뷰 반영 | `<ID> fix: …` | 작업 세션 | 없어도 됨 — 고칠 것이 없으면 없다 |
| ⑥ 마무리 | `<ID> done: …` | 작업 세션 | 필수 |
| 합치기 | `<ID> merge: …` | 리드(부명령 `merge`) | 없어도 됨 — 끝 확인 뒤에 부명령 merge가 남긴다 |

- 커밋 제목은 `<ID> <단계>: …`, 단계 차례는 표 차례(`req`·`plan`·`plan-review`·`test`·`run`·`review`·`fix`·`done`·`merge`) — 부명령 `status`가 이 차례로 찍는다. 필수 단계 커밋이 없으면 끝 확인(부명령 `end`)이 "빠진 단계"로 막는다. 커밋이 없는 단계는 `git commit --allow-empty`.
- 여러 작업을 한 커밋에 묶은 제목 `<ID>·<ID> <단계>: …`은 단계 찾기(`status`·빠진 단계·Stop 훅)에서 각 작업의 그 단계로 친다. 할 일 커밋과 차례 판정은 `<ID> <단계>:` 꼴만 본다.
- 커밋하는 순간 PreToolUse 훅(부명령 `guard`)이 제목을 끝 확인과 같은 판정으로 본다 — 작업 세션은 이 작업 ID와 작업 세션 단계(`plan`·`plan-review`·`test`·`run`·`review`·`fix`·`done`), 리드 세션은 작업 ID로 시작하는 제목이 리드 단계(`req`)인지와 요구사항 파일을 새로 더하는 커밋의 ID. `merge` 단계 커밋은 부명령 `merge`만 남긴다. 제목은 `git commit -m`으로 쓴다(편집기·파일에서 읽는 꼴은 막는다).
- 할 일 번호: `test`·`run` 커밋은 제목에 할 일 번호 `#N`(여럿이면 `#2 #3`)을 넣는다 — `run` 커밋에 없으면 막는다. `test` 커밋은 시험 파일만(하나 이상) 바꾼다(시험 파일은 규칙 `src/rules/tests.json`의 `patterns`).
- 차례(끝 확인 `end`가 막는다):
  - 할 일 `#N`마다(`TDD 예외 — <까닭>` 할 일은 뺀다) `<ID> test: #N …` 커밋과 `<ID> run: #N …` 커밋이 있고, 첫 `test` 커밋이 첫 `run` 커밋보다 앞(topo 차례).
  - 단계마다 첫 커밋은 아래 "단계 사슬"의 앞 단계 첫 커밋 뒤(앞 단계 커밋이 없으면 "빠진 단계"가 막는다).
  - 첫 `test` 커밋 앞의 `plan`·`plan-review` 커밋은 구현 파일(시험 파일·기록 폴더·`.md` 밖)을 건드리지 않는다.
  - 첫 `plan-review` 커밋 때의 `plan.md`에 없던 `TDD 예외`는 `## 구현하며 바뀐 것`에 `할 일 N`과 까닭이 있어야 한다.

단계 사슬 — 작업 세션은 단계마다 시작 명령 `step <단계>`로 들어간다. 그 단계의 앞 단계 커밋이 있어야 들어가고, 커밋하는 순간 PreToolUse 훅이 같은 사슬과 시작 명령으로 들어왔는지를 다시 본다. 앞 단계는 단계 차례에서 그 단계 앞으로 거슬러 처음 만나는 필수 단계(사이의 필수 아닌 단계는 없어도 된다) — 단계에 `start_after`가 있으면 그 단계. 앞 단계로 되돌아가기는 된다. 리드 몫 단계는 시작 명령 대상이 아니다:

| 단계 | 시작 명령 | 앞 단계 커밋 |
| --- | --- | --- |
| ⓪ 요구사항 | 리드가 커밋 | — |
| ① 설계 | `step plan` | `<ID> req:` |
| ② 코드 전 검토 | `step plan-review` | `<ID> plan:` |
| ③ 구현 — 시험 | `step test` | `<ID> plan:` (`start_after`) |
| ③ 구현 | `step run` | `<ID> plan-review:` |
| ④ 코드 뒤 검토 | `step review` | `<ID> run:` |
| ⑤ 리뷰 반영 | `step fix` | `<ID> review:` |
| ⑥ 마무리 | `step done` | `<ID> review:` |
| 합치기 | 부명령 `merge` | `<ID> done:` |

- 리뷰어 기다림(작업 세션 Stop 훅이 되돌린다, 보고는 작업 기록 폴더 기준):
  - 코드 전 검토 중 = `plan` 커밋 뒤 `plan-review` 커밋 전, 보고 `agents/plan-reviewer.md`가 다 있기 전 — 할 일을 아직 안 썼거나 TDD 예외 아닌 할 일에 `<ID> test: #N …` 커밋이 없으면.
  - 코드 뒤 검토 중 = 할 일이 모두 `[x]`이고 `run` 커밋 뒤 `review` 커밋 전, 보고 `agents/behavior-reviewer.md`·`agents/docs-reviewer.md`가 다 있기 전 — retro `## 끝 검증`에 `- <명령> → <결과>` 줄이 없으면.

합치기(부명령 `merge`, 리드)의 단계 — 실패하면 출력에 멈춘 단계가 나온다. 합친 뒤 단계(푸시·알림)는 없다:

| 단계 | 하는 일 | 값 |
| --- | --- | --- |
| ① 확인 | 세션 기록이 있고 작업 세션 프로세스가 멈췄고 워크트리가 있다, 워크트리에서 끝 확인(end) 통과 | 고정 |
| ② deliver | deliver로 넣기 — 리베이스(통합 브랜치 위로) → 프로젝트 검사(비면 건너뜀) → 합치기 전에 기록 커밋(작업 목록 `끝`·장부 번호·회고 `## 닫을 장부 줄`대로 장부 줄 닫기)과 끝 확인 다시 → fast-forward | 밖에서 받음 — 설정 `deliver.verify` |
| ③ 치우기 | 세션 닫기(세션을 연 터미널 프리셋 또는 custom 닫기 틀) → 작업 세션 claude 멈춤 기다림 → 워크트리·작업 브랜치 지우기 → 세션 기록을 done/으로 | 고정 |

## 리드 몫

### ⓪ 요구사항

1. 번호: `<작업 목록>`의 다음 `<ID>`와 결정 번호 범위(쓰인 마지막 다음부터, 작업마다 한 덩이 — 예: 10개). 열린 작업 브랜치 번호도 피한다. 번호는 요구사항 파일과 작업 목록 줄을 함께 만들 때만 생긴다 — 아직 없는 번호를 다른 문서에 적어 예약하지 않는다(받을 일은 `<장부>` 줄로 둔다).
2. 리드 체크아웃 `<통합 브랜치>`에 `<기록 폴더>/<ID>-<슬러그>/requirements.md`(`templates/requirements.md` — 머리 칸과 절을 모두 채운다, 부명령 `open`이 틀과 대조해 어긋나면 열지 않는다)와 작업 목록 줄 `| <ID> | <작업> | 진행 | NNNN~NNNN |`. 사용자가 정한 것은 그대로 옮긴다. 커밋 `git commit -m "<ID> req: 요구사항"` — 요구사항 파일을 새로 더하는 커밋의 제목이 그 ID로 시작하지 않거나, 작업 ID로 시작하는 제목이 리드 단계 꼴이 아니면 PreToolUse 훅이 막는다. 작업 세션은 커밋된 이 문서를 읽고 시작한다.
3. 이 흐름 밖의 몫(다른 세션·다른 팀)은 `<장부>` 줄로 둔다. 작업이 실을 줄은 상태 `요구사항 <ID>`로 둔다 — 작업 세션이 회고 `## 닫을 장부 줄`에 닫는 법을 적고 합치기가 옮겨 적는다.

### 작업 세션 열기

`python3 "${CLAUDE_PLUGIN_ROOT}/src/scripts/quest/main.py" open <ID> --lead <리드 세션 이름>`(리드 체크아웃에서, 먼저 `--dry-run`). 만드는 것: 작업 브랜치(`quest/<ID>-<슬러그>`), 워크트리(`<리드 저장소 부모>/<저장소 이름>-<id 소문자>`), 세션 기록 자리(`<git 공통 자리>/satchel/quest-sessions/<ID>/`)의 세션 settings(deny만)·시작 지시 `task.md`·상시 프롬프트 `standing.md`·기록 `session.json`(단계 기록 `steps.json`은 `step`이 쓴다), 워크트리 `.quest-session/orders.md`(지시 장부 — 그 폴더의 `.gitignore`로 git이 잡지 않는다). 작업 세션은 늘 `claude --model <설정 session.model> --dangerously-skip-permissions --plugin-dir <플러그인>`으로 뜬다 — 플러그인 훅이 늘 걸린다(따로 설치 범위를 맞추지 않는다). 시작 지시는 "먼저 `step plan`"이다. 통합 브랜치에 `<ID> req:` 커밋이 없거나, 필수 설정이 없거나, 고른 터미널 프리셋의 실행 파일·환경 변수가 없거나, 워크트리 자리가 리드 저장소 안이면 열지 않는다.

- 세션 띄우기: 설정 `session.terminal`의 프리셋(`src/presets/terminals.json`)으로 — `tmux`는 리드가 든 tmux 세션에 새 창, `orca`는 리드 탭의 Orca 워크트리(`ORCA_WORKTREE_ID`) 아래 새 탭, `custom`은 설정 `session.launch` 틀. 고른 터미널과 핸들을 `session.json`에 적는다(orca가 핸들을 끝내 못 받으면 "탭은 떴을 수 있다"를 알린다 — 탭을 찾아 `handle`에 적는다). `none`이면 띄울 명령을 찍고 끝나니 리드가 새 터미널에서 그 명령을 돌린다.
- deny: 홈 settings deny(리드 경로는 워크트리로 옮김)·리드 체크아웃·세션 기록 자리·플러그인 자리·홈 settings.json·규칙 `src/rules/files.json`의 자리(워크트리 안)·`src/rules/git.json`의 막는 git 명령(`Bash(git …)`)·`<장부>`(워크트리 안 — 리드만 쓴다)·질문 창(`AskUserQuestion`). 막힌 자리 안 한 폴더만 고쳐야 하는 작업이면 `--open <폴더>`(여러 번) — 덮는 줄을 빼고 형제를 하나씩 막는다. deny를 손으로 고칠 때도 glob 문자 클래스(`[…]`)를 쓰지 않는다(Claude Code가 폴더 전체 막음으로 읽는다).

### 작업 세션과 주고받기

- `[<ID> → <리드>] 시작: ①`이 오면 보낸 이(from)를 `session.json`의 `session_name`에 적는다. 작업 세션이 멈추거나 확인 창에 걸리면 리드가 푼다.
- 결정 요청: 작업 세션은 사용자에게 묻지 않는다. `[<ID> → <리드>] 결정 요청: <asks 파일>`이 오면 리드가 정하거나(영역 안) 리드 세션에서 사용자에게 묻고(여러 요청은 모아서) `[<리드> → <ID>] 결정: <n> <고른 것>`으로 답한다.
- 막힘: `[<ID> → <리드>] [막힘] <막힌 명령과 까닭>`이 오면(커밋 나누기·가지 옮기기처럼 작업 세션에 막힌 일) 리드가 대신 하거나 길을 정해 답한다.
- 끝: `[<ID> → <리드>] 끝: <작업 폴더>/retro.md`가 오면 합친다.

### 합치기

`python3 "${CLAUDE_PLUGIN_ROOT}/src/scripts/quest/main.py" merge <ID>`(먼저 `--dry-run`). 단계는 셋("단계와 커밋"의 합치기 표, 정본 `src/rules/flow.json`의 `merge`):

1. ① 확인 — 작업 세션 프로세스가 멈췄고 워크트리에서 끝 확인(`end`) 통과.
2. ② deliver — `quest merge`가 안쪽 부품 deliver(`src/scripts/deliver/`)를 코드에서 부른다: 리베이스 → 프로젝트 검사(설정 `deliver.verify`, 비면 건너뜀) → 합치기 전에 기록 커밋과 끝 확인 다시 → `<통합 브랜치>` fast-forward.
3. ③ 치우기 — 세션 닫기(세션을 연 터미널로 — orca는 쉼을 기다린 뒤 탭 닫기, tmux는 창 닫기, custom은 설정 `session.close`, none·핸들 없음은 건너뜀, 실패해도 이어 감)·작업 세션이 멈추기 기다림 → 워크트리·작업 브랜치 지우기 → 세션 기록을 `done/`으로.

멈추면 출력 `quest merge — <단계>에서 멈춤: …`(② 안이면 deliver 단계 — 확인·리베이스·검사·합치기 전·합치기 — 도 함께). 막히면 까닭과 함께 작업 세션에 돌려보낸다. 작업 세션이 아직 돌아 ③에서 멈추면 세션을 끝내고 다시 부른다(병합은 끝났다). 합친 뒤 단계(푸시·알림)는 없다.

- 기록 커밋 `<ID> merge: README 끝·넘길 일 <장부 ID>…·장부 닫음 <장부 ID>…` — 작업 목록 줄 `끝(<마지막 작업 커밋>, 로컬)`, 회고의 번호 없는 넘길 일마다 다음 장부 번호를 `<장부>`에 `열림`으로 더하고 회고 항목 끝에 `[<장부 ID>]`, 회고 `## 닫을 장부 줄`의 줄마다 `<장부>` 그 줄의 상태·근거 칸을 고친다. 그 절을 읽지 못하거나(절 없음·꼴·근거 틀림·장부에 없는 줄·이 작업 줄이 아닌 줄) 고친 뒤 `요구사항 <ID>` 줄이 남으면 합치기 전에 멈춘다 — 작업 세션에 돌려보낸다. 본문 `리드 끝 검증: <deliver.verify> → 통과`(돌렸을 때), `--verified "<글>"`은 `메모:` 줄일 뿐 판정이 아니다. 리베이스 뒤라 번호·해시가 `<통합 브랜치>` 기준이다.
- 바뀐 규칙 문장(설정 `quest.rule_docs`의 `patterns`가 있을 때만): 부명령 `merge`가 ② 병합 뒤 회고 `## 바뀐 규칙 문장` 줄을 그대로 찍는다 — 리드는 사용자 보고에 옮긴다.

푸시는 사용자 지시 때만. 사용자에게: 요구사항·회고 경로, `python3 "${CLAUDE_PLUGIN_ROOT}/src/scripts/quest/main.py" status <ID>` 단계 시각, 결정 n개·리뷰 Critical/Important 수·넘길 일·(켰으면) 바뀐 규칙 문장(옛 → 새).

## 작업 세션 몫

같은 세션이 ①~⑥을 끝까지 간다. **단계마다 먼저 `python3 "${CLAUDE_PLUGIN_ROOT}/src/scripts/quest/main.py" step <단계>`를 부르고 나온 안내를 따른다** — 앞 단계 커밋이 없으면 멈추고 무엇을 먼저 할지 알려 준다(앞 단계로 되돌아가기는 된다). 안내는 그 단계에서 할 일·쓰는 틀과 리뷰어·지킬 것·마치는 조건·커밋 제목 꼴·다음에 부를 명령과, 모든 단계에 같은 것(결정하는 법·결정 요청·막힘·커밋 꼴 — `steps/common.md`)이다. 시작 명령 없이 그 단계를 커밋하면 PreToolUse 훅이 막는다.

| 단계 | 시작 명령 | 안내 |
| --- | --- | --- |
| ① 설계 | `step plan` | `steps/plan.md` |
| ② 코드 전 검토 | `step plan-review` | `steps/plan-review.md` |
| ③ 구현 — 시험 | `step test` | `steps/test.md` |
| ③ 구현 | `step run` | `steps/run.md` |
| ④ 코드 뒤 검토 | `step review` | `steps/review.md` |
| ⑤ 리뷰 반영 | `step fix` | `steps/fix.md` |
| ⑥ 마무리 | `step done` | `steps/done.md` |
| 모든 단계 | (함께 찍힌다) | `steps/common.md` |

## 훅이 하는 일

- PreToolUse 훅(플러그인 `src/hooks/hooks.json` → 부명령 `guard`), 작업 세션: 질문 창, 공용 머리말 없는 하위 에이전트, git 되돌리기류·리드 저장소 쓰기·막는 git 명령(규칙 `src/rules/git.json` — open이 세션 기록에 guard 목록으로 적는다)·셸 매개변수 가공·glob 뒤 `..`·deny 자리 읽기·쓰기(리다이렉트·인터프리터 본문·patch 포함)를 막는다. `git commit`은 제목이 "단계와 커밋"의 꼴(이 작업 ID·작업 세션 단계·`run`의 `#N`)이 아니거나 제목을 읽을 수 없는 꼴(`-m` 없이 편집기를 여는 커밋·`-e`·`-F`·`-C`/`-c`·`--fixup`/`--squash`)이면 막고, 단계 사슬의 앞 단계 커밋이 없거나 그 단계를 `step <단계>`로 들어오지 않았으면(세션 기록 `steps.json`, 기록이 깨졌어도) 막는다 — 커밋은 `git commit -m "<ID> <단계>: …"`로 한다.
- PreToolUse 훅, 리드 세션: quest 설정이 있는 저장소의 `git commit`만 본다 — 작업 ID로 시작하는 제목은 리드 단계(`req`) 꼴(`merge` 제목은 부명령 `merge`만 남긴다), 요구사항 파일을 새로 더하는 커밋은 그 ID로 시작. 그 밖은 아무것도 하지 않는다.
- Stop 훅(플러그인 `src/hooks/hooks.json` → 부명령 `hold`), 작업 세션: `대기: 사용자`로 끝내기, 리뷰어를 기다리며 할 일이 남은 멈춤("단계와 커밋"의 리뷰어 기다림), 결정 요청 뒤 깨우기 예약 없음을 되돌리고, 턴 끝 두 줄(`남은 지시:`·`대기:`)이 없으면 상시 프롬프트를 다시 넣고, 지시 장부에 대기 사유 없는 열린 항목이 있거나 열린 항목이 있는데 `남은 지시: 없음`이면 되돌린다.
- 끝 확인(부명령 `end`)은 끝에 한 번 — 기록 파일 넷과 절, 요구사항 틀 칸, 커밋 차례, 반영 표, 넘길 일 꼴, `## 닫을 장부 줄`과 장부 대조, (켰으면) 바뀐 규칙 문서마다 회고 줄. 합치기가 다시 부른다.
